# Declarative appearance: details, badges, connection points and rows, changed trait by trait

A declarative component's appearance, and an element's own, can say more than its shape, colours and size. `detail` says what its shapes write under the element's name: whether the component's name, the values of chosen attributes, and badges, short texts such as "PK" written while a boolean attribute is true or while the element is the `from` end of a relation of a given relation type, or of one derived from it. `connectionPoints` names places on the border, each on one side at a place from 0 to 1, where relations attach: a relation attaches to the connection point facing its other end and stores nothing about it; an empty list has relations attach anywhere on the border, whatever is inherited. `contentsAsRows` draws what an element holds as rows (ADR 0023). An attribute definition can list `choices` for a string and a `unit` for a number; a value outside the choices only warns. A relation type's limit for an end is a list of at least one id, or `any`, which lifts a limit it would inherit. Every trait is inherited from the nearest definition that sets it, each part of the detail on its own, up to Essence, which writes the component's name and has no badges, no connection points and no rows. The project's own components, relation types and packages change through commands that change only the traits they name (`update-component`, `update-relation-type`, `update-package`), where `null` takes a trait out so that it is inherited again; renaming an attribute moves the values, details and badges that get it from that definition, and nothing where a nearer definition redefines it; a relation type cannot stop nesting while a view nests by it. Creating a definition can be create-only: with `createOnly`, the command is refused when its id is taken, so the app and Claude never overwrite each other's new definitions, and replacing one stays a separate, explicit command. Without an id, the core makes one: its package's id, a dot, a base made from its name and six random base-36 characters, as ADR 0019 makes element ids, so a removed id never comes back. The core checks every value a command sets, with a stable problem code for each refusal, and only warns, on open, about what a file already holds. The format stays at version 1: every new key is optional, so nothing already stored changes; a project saved in a newer format is refused with a message that says so, never with the schema's message about a constant. We chose this because the spec promises a label, an icon and connection points for a shape's look, because inheritance must stay the one rule people learn, and because once Claude edits through MCP, replacing whole definitions would let the app and Claude silently undo each other's changes.

## Considered options

- **A relation storing which connection point it uses**: rejected for now. Attaching to the facing point covers rows and most components and keeps drawing choices out of the model.
- **`null` in files for "nothing"**: rejected. Commands use `null` to inherit; files say `any` or give an empty list.
- **Only whole redefinitions**: rejected. An editor holding an old copy would undo a change Claude just made.
- **Definition ids made from names with a counter**: rejected, as ADR 0019 rejects them for elements. A removed definition's id would come back, and a branch merged later would show its elements as the new definition.
- **Conditions or formulas in attribute values**: rejected. They are code (ADR 0012).
- **Refusing every later change while a file breaks a rule it was opened with**: rejected. A detail that names an unknown attribute only warns on open, and blocks only changes to that detail or to what it can name.

## Consequences

A build without these keys refuses files that use them, so the schemas are regenerated and committed with the change. Two constraints tighten: a file with an empty limit list, which used to allow nothing, or with an appearance width or height above 100,000 no longer opens. None exists today, and the test generators are narrowed with the change. Images join the appearance's traits with M3b, under their own decision; the list of traits is checked at compile time, so adding one without its resolution and its check does not build. The inspector changes an element's own appearance trait by trait, through `update-element`'s `appearanceTraits`.
