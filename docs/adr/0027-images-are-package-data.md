# Images are package data, cleaned in the core and drawn only as decoded pictures

An image is a picture a package defines, next to its components, in its `.vapackage`: SVG text, or the bytes of a PNG, JPEG or WebP bitmap in base64, each with an id that starts with its package's id. A package without images leaves the `images` key out, so that undoing the first image gives the file back exactly. An appearance, a component's or an element's own, shows an image by id, as an icon beside the name or as the shape's whole drawing, optionally as a silhouette of one color, or says `none` to stop an inherited one; one image serves any number of components and elements, and an element's own picture lives in one of the project's own packages. These choices follow:

- **Cleaned before it is stored, whoever sends it.** `define-image` stores only what cleaning gives and reports what it removed (`image-cleaned`). SVG is read by a strict reader and a new document is written from an allow-list: shapes, paths, groups, `use`, gradients, clipping and masks; `a` and `switch` unwrapped; paint from attributes, `style` attributes and `<style>` rules that select by a class or an element name, folded into attributes; references only as `#id` or `url(#id)` to the picture's own parts; values from a narrow character class, with only color and transform functions; text, scripts, foreign objects, animation, images, filters, patterns and markers dropped. DOCTYPEs, entities other than XML's own and malformed markup are refused (`invalid-image`). A bitmap's type and size are read from its header before anything decodes it, and it is rebuilt from an allow-list of its chunks or segments (a JPEG keeps its arithmetic-coding tables too), which drops text, EXIF with its GPS position, color profiles and times.
- **Caps bound every cost** (`image-too-large`), each a named constant in the core:
  - SVG input: 512 KiB, 20,000 elements, nesting 256 deep, 256 namespace declarations, 256 style rules, 16 selectors a rule, 1,024 declarations in the rules that fold (counted once per selector), and 100,000 folding steps in all (each declaration applied and each rule an element finds), so that no product of capped factors makes cleaning slow;
  - SVG output: 4,000 weighted elements (a mask reference weighs 64, a clip 16, an opacity below 1 16 with children and 4 without, and a `use` what it refers to; elements kept are counted before their styles fold), depth 24, 64 `use` elements that never refer to a part holding one, 32 gradients of at most 16 stops, 16 clip paths and masks that never hold or refer to another, 20,000 path commands, 64 KiB of text, a view box of at most 100,000 a side, dash patterns of at most 16 entries none finer than 1/1000 of the view box's diagonal, and stroke widths clamped to it;
  - bitmaps: 192 KiB once stripped, 1,024 pixels a side and 1,048,576 in all, never animated, and a JPEG of at most 64 scans;
  - a package: 128 images and 2 MiB of image text; opening warns from 1 MiB, and images past 2 MiB in file order are not drawn (`large-images`).
- **One cleaned view, for every reader.** The core keeps the cleaned view of each stored image, cached by its content and pruned to the open project's images; the canvas, layout, previews and Claude's tools read only that view, typed so that a stored image cannot be passed in its place. Opening a project warns about an image that cleaning would change (`image-not-clean`) without rewriting its file, treats one that cleaning refuses as absent (`invalid-image`), and warns about appearances that show an image no package defines (`unknown-image`).
- **References are checked once a command is done.** Whatever commands an action runs, a batch included, every image an appearance comes to show must be defined by a package in use and written as a reference (`unknown-image`, `invalid-command`), and no image that an appearance still shows may go, on its own or with its package (`in-use`).
- **Transport and drawing.** Images reach the app only inside the project over the live connection, never through an HTTP route; the connection takes messages of at most 4 MiB and closes with code 1009 past that. The app draws an image only by decoding it as a picture into a canvas or a texture: bitmaps with `createImageBitmap` at the size they are drawn, SVG through a Blob URL into a detached image, revoked once decoded. It never turns text into markup in the page, which ESLint enforces.
- **The page's policy.** The built page's content security policy allows only its own scripts (and its own inline scripts, by their hashes), connections only to the local program, workers only from its origin, no objects, base or forms, no framing, and strings turned into HTML only through its `default` Trusted Types policy, which accepts only the empty string as HTML and only scripts of the page's own origin. PixiJS's `unsafe-eval` entry point keeps `'unsafe-eval'` out. Every JavaScript response carries a worker policy that allows no connection, so a worker holding a copy of the project cannot send it anywhere. Dev mode uses the same page policy without Trusted Types, because Vite's error overlay writes HTML, with a nonce on the scripts Vite writes (not on styles, where a nonce would switch `'unsafe-inline'` off); and it refuses any request that names a file inside the project folder's real path, through `/@fs/`, `/@id/` or the app's own root.

We chose this because ADR-0012 already requires a declarative component's drawing to be data stripped of scripts and external references; because keeping images in package files gives them every guarantee project files have (validation on open, stable writing, atomic saving, exact undo) without a new kind of file, route or upload; and because a picture that reached the page as markup, or a cleaner whose cost grew with the product of its input's parts, would let a shared project run code or stall the local program.

## Considered options

- **Image files in an `images/` folder served by the local program**: rejected for v0.1. A non-JSON file kind changes ADR-0013's folders of JSON files and the rule that project files are JSON, and needs a token-checked HTTP route, a content policy for SVG, binary saving kept in step with undo, and a watched folder. It stays the path for large photos, under the same ids.
- **SVG only**: rejected. Photos of people and places are what a system's diagram often lacks, and small bitmaps cost little once capped.
- **Images inline in each appearance**: rejected. A picture would be stored once per component and element, and every replace of an element would carry it.
- **Drawing SVG through PixiJS's SVG parser**: rejected. It parses the markup in the live page.
- **Cleaning by removing known-bad parts**: rejected. Only an allow-list cannot miss a construct nobody thought of.
- **Readers using the stored form of an image pulled from git**: rejected. Text and metadata that cleaning drops would reach Claude and the canvas.
- **Each factor capped on its own**: rejected after a security review. Thousands of elements under thousands of rules made a small file cost billions of steps; the total work is capped instead.
- **Checking image references in each command that sets an appearance**: rejected. A check after the action covers every command, the ones added later included.

## Consequences

An image is one long line in a diff, so sizes are capped. Text inside an SVG is dropped, so pictures keep only shapes, and a `switch` draws all its alternatives. A picture whose first rasterization in the app takes over 16 ms is shown as its shape's placeholder for the rest of the session. The schemas are regenerated with the change, and a build without it refuses files that hold images. Exports will need to draw images.

## How M3b draws images and picks them

These clarify `docs/designs/components.md` §5.4 and §5.7 where they left a choice open.

- **Where a picture goes** is worked out in the scene from the cleaned view's width and height (`canvas/shape-images.ts`), never from decoding:
  - beside the name on a plain shape, in the square §5.7 gives, the text moving right of it;
  - in the header of a shape that holds contents, a collapsed container and a shape that draws rows, whatever the placement asks;
  - as a drawing: the picture on a plate 4 units larger, above a name band across the shape, the two centred together in the shape. When the shape leaves the picture less than 8 units a side, the drawing is drawn as an icon instead.
- **A drawing's `plate`** is the plate and the band under it, as wide as the plate. Routes and the selection's and hover's marks go by it. Pointing finds the drawing by its plate and by its whole name band, so that a name wider than its picture can be clicked; the empty space beside them is what holds the shape.
- **The placeholder of a drawing** is its shape's own outline, drawn by the tile's full drawing just inside the plate. The image drawing covers it with the plate and the picture once the texture is ready, so a picture that never decodes leaves the outline, and an icon's placeholder is nothing.
- **The name under a drawing** is written in colours read on what the shape sits on, in the theme shown: its container's fill in that theme, or the canvas. The painter finds it when it writes the label and again when it tints labels for a switch, and a tile that holds a drawing has labels that follow the theme, whatever the drawing's own colours. Recolouring a container does not yet tint again the names under the drawings it holds.
- **Pictures in the dark theme** (ADR-0033): the picture is drawn as stored in both themes, a silhouette in its stored colour. A plate is drawn in white, in a drawing of its own for each pair of a fill and its dark shade, and tinted each frame to the fill of the theme the canvas shows, so that a switch changes plates in the frame it shows, with the rest of the canvas, and nothing is drawn again for it. The placeholder outline and a drawing's block far out are drawn by the painter, and restyled as every tile is. A drag draws its plates in the theme's fill, and is drawn again when a switch shows.
- **Image drawings.** Each tile of shapes with pictures gets a render group of its own just above its full drawing, holding the drawings and then the icons, so that rebuilding it gathers only that group again and icons hide at once below names' scale. It is rebuilt when a texture it waited for arrives, and when the zoom or the camera resting changes the bucket its pictures want: at most four a frame, those whose textures arrived first, then nearest the middle of the screen, and none once the frame has spent 8 ms. A tile made by an edit in place of one drawn in full draws its pictures at once with the textures already made, and so does a drag. The scene's pictures prune the store and the serials whenever another scene is shown.
- **The store** asks for a frame when a picture arrives or fails, says when it left work for the next frame, and can be cleared for the benchmark's cold runs. Serials live in a module without PixiJS, since the layout worker loads the scene, and pruning goes by serial, only when the pictures a scene shows change.
- **What a frame costs.** An atlas page keeps its pixels on the CPU, in a buffer source, and a frame uploads only the rows of the cells drawn into since the last one, rather than the whole 16 MiB page. Textures of their own, past the atlas, are made one a frame. Nothing is decoded or uploaded while the canvas is zoomed out past every picture's scale. At rest, an SVG is rasterized at a bucket only when its cost, estimated from the buckets measured and grown with the pixels, keeps the frame within 16 ms; a picture too costly at the bucket its size asks for is drawn from the largest one made, and the next bucket up is rasterized and measured, until the estimate says no more.
- **The picker** offers "Choose an image…", also by dropping a file on it, and "Use a picture already in the project", a grid of previews drawn into canvases; then the placement and the silhouette, a colour that starts at the canvas's dark grey. The component editor keeps its way back to the inherited image and its "Show no image"; an element offers "Use the component's image" and "Show no image". Pasting SVG text is left out.
- **Where a picture is stored**: a component's in its own package; an element's own in the package of its component when the project owns it, else in the first of the project's own packages, else in a new package named after the project, in the same action. Content the package already holds reuses its id. An action that only changes how a picture is shown is one update; one that defines a picture is a batch named `Set the image of "…"`.
- **Preparing a file**: a file over 64 MiB is not read. Headers are read before decoding; over 16,384 pixels a side or 64 megapixels is refused. A PNG, JPEG or WebP within the caps goes through the core's cleaner as it is; anything else the cleaner refuses, animated pictures included, is decoded, first frame only, and encoded again as §5.4 says. The report lists what cleaning removed in the core's words, which stay in English.
- **The "images" benchmark** (`?images`) holds 10,000 shapes: every element in a system shows one of 20 SVG icons, 4 of them at the caps on elements, path commands, gradients, and clips and masks; 300 spread evenly show one of 300 distinct 48-pixel PNGs as their drawing, in three packages of 100. In work mode it lets pictures arrive between frames, which the canvas does not draw on its own meanwhile, and three phases start with the store cleared, at scales not drawn before.
