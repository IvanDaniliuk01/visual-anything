# Packages extend the app with actions, importers, exporters and panels, still sandboxed and approved by their hash

Package code (ADR 0012, 0054, 0060) can compute attributes, check elements, draw inside shapes and simulate (ADR 0085). It cannot add anything a person does: a menu item, an importer, an exporter, a section of the inspector, an action Claude can run. Those are written into the program. The user wants plugins that add improvements to the system, as draw.io's Plugins… menu does. In Visual Anything a plugin is a **package**: the glossary keeps that word and avoids "plugin" (CONTEXT.md), so the menu reads "Packages…".

## Decision

- **Package code may export four more hooks, each a pure function answering plain data**, run as every hook is: in QuickJS in the code worker, within ADR 0054's limits per call, only after the person approves the code by its hash, with only the capabilities they grant:
  - **`actions`** lists named actions, each with a label, where it shows (the canvas menu for a selection, the Packages menu, or both) and the components it applies to. Running one calls the hook with a frozen copy of the selection and, with `model:read`, the model, and it answers a **proposal** (ADR 0073): commands the person reviews and accepts or declines. An action never changes the model by itself. What is accepted is recorded with the person as its author; Claude's runs wait as Claude's proposals.
  - **`import`** declares the file extensions it reads. Given a file's text, it answers a proposal that builds what the file describes, reviewed as any proposal.
  - **`export`** declares a format's name and extension. Given the model and a view, it answers a text, which the local program writes where the person chooses. It never writes files itself.
  - **`panel`** answers a section of the inspector for a selection as data: headings, read-only values, tables, charts of numbers, and buttons that run the package's actions. The app draws it with its own controls; package code never touches the page (no HTML, no DOM).
- **Claude reaches them through two generic tools,** `list_package_actions` and `run_package_action`, rather than tools a package adds, so Claude's tool list stays fixed and every run is a proposal.
- **"Packages…", in the app's menu,** lists the project's packages, built-in and its own: what each adds (components, relation types, hooks, actions, importers, exporters, panels), its capabilities, its approval, and switches to turn a package's hooks off for this computer (a preference, ADR 0032). It adds a package from a `.vapackage` file or a folder on this computer, shows the code before the first approval, and updates one from a newer file, asking for approval again since the hash changed. There is no download from a registry; a marketplace stays not planned.
- **Results are validated before they are used:** a proposal's commands go through the core's checks as any command does, an export's text is capped in size, and a panel's data is checked against its schema and capped. A hook that fails or runs out of time shows a notice naming its package and is not retried automatically.
- **Built-in packages may use the same hooks,** so new improvements can ship as packages: for example a SQL DDL exporter in Data modeling, or "Find tables no relation reaches" as an action.

## Considered

- **Packages running UI code (iframes, HTML, React components):** rejected. It would break ADR 0012's sandbox, the project's rule against storing code that runs outside package code, and the read-only page's security (Trusted Types). Data-only panels keep the app's look and accessibility.
- **Actions applying commands directly:** rejected. A proposal keeps the person in charge and the history clear, and it costs one click.
- **Packages adding MCP tools of their own:** rejected for now. Claude's tools would change with each project, and descriptions written by packages would reach Claude's instructions.
- **Layout algorithms from packages:** left for later. Layout runs in its own worker within a frame budget (ADR 0015), and QuickJS is too slow for 10,000 shapes.
- **A registry to download packages from:** not planned (spec, "Not planned"); a shared package is a file.

## Clarifications

- 2026-11-02 (M14.0, the seam, in the main session):
  - **Declared in the file, run by the code.** What a package adds is declared in its file, `extensions: { actions, importers, exporters, panels }`, so that the app lists it in menus, in Import… and Export… and in the inspector before the code is approved or runs; each runs through one hook named for its kind, `act`, `importFile`, `exportFile` or `panel`, called with the declaration's id. The hooks are not called `actions`, `import` and `export`, since `import` and `export` are JavaScript's own words. An action has an id, a label, an optional description, where it is offered (`selection`, `packages-menu`, or both) and the components it is offered for; an importer, the extensions it reads; an exporter, the one it writes; a panel, the components it shows for. At most 32 actions and 8 of each other kind; ids are lower case letters, digits and `-`, unique within their kind; labels are 1 to 60 characters, in the package's own words.
  - **They go with the code, and in its hash.** `set-package-code` takes `extensions`, as it takes capabilities: `null` removes them, and they are removed with the code. The hash a package is approved by is `[text, capabilities, extensions]` when it declares any, with their keys sorted, and stays `[text, capabilities]` otherwise, so that every approval given before ADR 0089 holds while adding an action asks again.
  - **What the hooks answer.** `act` and `importFile` answer `{ label?, commands }`: at most 500 commands, within 1 MiB as JSON, none that creates, edits, resolves or deletes a comment, resolves conflicts or writes package code, in batches too. `exportFile` answers a text of at most 4 Mi characters. `panel` answers at most 64 blocks, each a heading, a text, a value, a table (up to 12 columns and 200 rows), a bar or line chart (up to 6 series of 200 values), or a button that runs one of the package's own actions. Each is checked by `core/src/code/extensions.ts` and kept rebuilt from the parts its kind has, or dropped whole with the reason.
  - **Longer calls for what the person asked for.** `act`, `importFile` and `exportFile` run up to 2,000 ms a call, since the person waits for them with a notice; `panel` keeps ADR 0054's 50 ms, since the inspector calls it as the selection changes. Memory stays 32 MiB.
  - **Changes for review are not Claude's proposals.** An action or an importer the person runs answers changes the core shows with `previewPackageChanges`: the comparison of the project now and with them (ADR 0070), and the one batch command that applies them all as the person's action, refused whole when one breaks a rule. Choosing some of them is left out for now. Claude's runs (M14.5) go through Claude's proposals (ADR 0073) as any command of Claude's does.
  - **The protocol's messages** for running actions, importers and exporters, which the seam was to hold, go with M14.3 and M14.5, which know where each runs: package code runs in the app's code worker, and Claude's tools run it in the local program.
- 2026-11-02 (M14.1, the worker, by a builder):
  - **What the code is called with.** Each hook is called `hook(input, context)`: `input` is the core's `ActionInput`, `ImportFileInput`, `ExportFileInput` or `PanelInput`, rebuilt from its own parts and deep-frozen, and `context` holds only `model`, with `model:read` granted, which reads the project as it is when the call runs. Without `model:read` an action sees the ids it is given and no more: what the selected elements are as the canvas's hooks see them is not handed over, so that Claude's runs in the local program (M14.5) can be called the same way. `context.fetched` stays `attributes`'s, and `time` is the clock as elsewhere.
  - **Only what is declared, only approved code.** The worker refuses, without calling any code, a call for a package it does not run or whose code does not hash to its approval, one turned off or that failed to load (with that problem), one for an id the package's file does not declare, and a file over `CODE_LIMITS.importText` characters, which the app also never sends. The canvas's rounds call only `attributes`, `check` and `draw`; the four new hooks run only when asked.
  - **A call runs alone, ahead of the other work.** A QuickJS call cannot be cut into slices: it runs to its end on the worker's thread. So a call of a hook that adds to the app runs between two slices of the canvas's hooks or of simulation runs, ahead of them since the person waits for it, and while it runs, up to 2 s for `act`, `importFile` and `exportFile` and 50 ms for `panel`, the canvas's hooks wait and answer again once it ends. A second worker with its own interpreter, which would keep them answering, was left out: it would load every package's code twice, in a second WebAssembly interpreter, on the weak machines the app aims at, and it would need the two workers to agree on the stops that turn a package off. The worker says `extension/running` as a call starts, so that the app's watchdog waits the hook's time longer before it thinks the worker stalled; the notice that a call runs is the app's to show while its promise waits (M14.3, M14.4).
  - **Answers and failures.** An answer goes through `checkChangesAnswer` (with the action's or the importer's label when it gives none), `checkExportAnswer` or `checkPanelAnswer` (with the package's declared action ids). The sandbox lets an answer reach the check as long and as deep as the check takes, 1 MiB nested 20 levels for changes and six characters as JSON for each of an export's, so that the core says why it drops one. A failure, a stop or a dropped answer comes back once as a problem naming the package, the hook and the label of what it was asked for (`extensionProblem`, `undeclaredProblem`, `fileTooLongProblem`), in Spanish too, and nothing is retried. A call stopped for its time or memory counts towards turning the package off as the other hooks' stops do; a call that answers ends the row. A worker that stalls during a call answers that call with `stalledProblem` and sends the calls that waited to the worker started again.
  - **The app's calls.** `PackageCalls` (`runPackageAction`, `readFileWithPackage`, `writeFileWithPackage`, `packagePanel`), each a promise of `PackageAnswer<T>`, `{ ok: true, value }` or `{ ok: false, problem }`, is implemented by the code worker's host and reached in the shell through `usePackageCalls()`; without approved code it answers that the package's code is not approved.
- 2026-11-02 (M14.2, "Packages…", by a builder):
  - **Where it is.** "Packages…" is an icon button in a group of its own at the end of the header's actions, after Import…, Export… and Copy address, named in its tooltip and to screen readers as Copy address and Compare with… are (A5.3): it is about the project, and the canvas toolbar's More holds the view's tools. It opens a dialog listing every package the project uses, in the order the project lists them, built in or its own: its name, version, how many components and relation types it holds, the labels of the actions, importers, exporters and panels its file declares, what its code may reach (with "not granted" for a capability the approval left out), and where its code stands: no code, waiting for approval, approved (and running), off after its calls stopped, failed to load, over 256 KiB, or turned off on this computer. Its "Review the code…" opens the approval dialog of ADR 0054, as the inspector does, which shows the code before the first approval and holds Withdraw approval; the Packages dialog hides under it, keeping what it holds, and the focus comes back to the button once it closes. A project that uses no package says to add one from a file or a folder.
  - **Turned off on this computer** is the preference `codeTurnedOff` (ADR 0032): the ids of the packages whose code this computer does not run, sorted, each once, at most 256, written after `sidePanels`, read leniently and checked strictly as every preference is. It is by package id, not by project, since a package keeps its id in every project it is copied to (ADR 0051), and the person turns off a package, not one copy of it. `usePackageCode` leaves a package turned off out of what the code worker is given, approved or not, so its code never loads; its approval stays, and turning it on again runs it under that approval. Calls of what it adds answer `turnedOffProblem` without asking the worker, and the notice that its code waits for approval is not said for it. The checkbox "Run its code on this computer", on by default, sets it.
  - **Adding and updating from a file go through the local program.** The person chooses a `.vapackage` file, or a folder, whose package files at its top and in its `packages/` folder are offered (at most 32, sorted by path). The browser reads the chosen file, at most 2 MiB, and sends its text with `package/read`; the local program parses it and checks it against the package file's JSON Schema, running nothing, and answers `package/read-answer` with the package, or `command/rejected` with what the schema found, at most 20 problems, each saying where ("In the package file, /name must not be empty."). 2 MiB keeps the message within the live connection's 5 MiB even if escaping doubled every character. These messages join protocol 7, as `drawing/make` did. The app then shows what the file does and sends one action, which the core checks as any command: a package with the id of one of the project's own updates it (`replace-package`, with ADR 0051's list of what changed and a note when the file's version is older); any other is added (`add-package`, which refuses a built-in package's id). Either is followed, in one batch named as the command alone would be, by `set-package-code` with the file's code, capabilities and what the code adds, since neither command carries them; `replace-package` keeps none of the code, so it is set again even when it is the same.
  - **Updating asks for approval again when the code changed.** The approval is by the hash of the code, its capabilities and, when declared, what it adds (M14.0), so a file whose code, capabilities or declarations differ runs only once approved again, and the preview says so before anything changes; a file with the same code keeps its approval, and says that too.
  - **What cannot come from a file yet.** A file with solids is refused, since their files live beside the project and a package file does not carry them; so is one with crosswalks, which no command adds yet, and one with conflicts from a merge, to be resolved in its own project.
- 2026-11-02 (the main session, on M14.2's questions): "Packages…" stays an icon in the header's one row; code turned off stays by package id, wherever the package is copied; packages with solids, crosswalks or conflicts stay refused from a file until a command can add them. **A bug M14.2 found, to fix in M14.3:** `replace-package` rebuilds a package without its `code`, `capabilities`, `extensions`, `solids` and `crosswalks`, so ADR 0051's "Update from another project" drops them; it must keep what the new file holds, the code asking for approval again as its hash changes.
- 2026-11-02 (M14.3, actions, importers and exporters, by a builder):
  - **Offered only when the code runs here.** A package's actions, importers and exporters are offered once its code is approved, not turned off on this computer, and neither off after its calls stopped nor failed to load; a package that waits for approval offers nothing, and "Packages…" says why. What each offers is what its file declares (`core`'s `extensions`, in the hash).
  - **Where actions show.** The shape menu has a group "From packages", after Show in physical space and before the stacking order, with each action whose `where` holds `selection`, in the package's own words, its description or "From the package “…”" as its tooltip; none in a comparison, and none run while the project cannot be changed. An action that names components is offered when the selection holds elements alone, each of one of those components or of one derived from them (`componentDerives`); one that names none, for any selection with an element or a relation. It is called with the selected elements, then the selected relations, and the open view. "Packages…" shows, in each package's entry, a "Run “…”" button for each action whose `where` holds `packages-menu`, called with the canvas's selection too; pressing one closes the dialog, so that the review shows on the canvas.
  - **The review is the comparison and the Changes tab, as for Claude's proposals.** While the code runs, up to 2 s, a status says "Running “…”, of the package “…”…". Its answer is previewed by `previewPackageChanges` on the project as the tab holds it then, whose result now also holds the project with the changes (`project`), the newer side of the comparison. The canvas shows it read-only (ADR 0070), and the Changes tab lists its changes with Accept and Decline above them, how many commands it holds, and that accepting makes them one action of the person's, which Undo takes back whole. Accept sends the batch through the editor, as the person's command, which the core checks again; a refusal is said by the usual notice and the review stays. Decline, the comparison's End or Escape drop the changes and send nothing. Ticking some of the changes stays left out, as M14.0 had it. One run at a time: another asked meanwhile does not start, and says so; a review replaces the one before. An action that answers no commands says so in a notice and opens no review; a failed call says its problem (M14.1's, translated); changes that break a rule say why, whole.
  - **Importers in Import….** The Format list offers each importer, "{label} ({extensions}), from the package “…”", and the file chooser accepts its extensions. As the file says, a file whose ending no built-in format reads goes to the first importer that declares it; a built-in format keeps its endings unless the importer is chosen. Reading runs `importFile` with the file's name and text (pasted text too), with a status in the dialog; once the code answers changes, the dialog closes and the review opens; what leaves nothing to review is said in the dialog.
  - **Exporters in Export….** Each exporter is one more format after the app's own, named by its label and "Written by the package “…”, as a … file", made when saved as a PDF is (its code runs then, and Stop making it lets go of the wait), saved by the browser as every export is, under the project's and the view's name with the declared extension. `exportFile` is called with the open view. The dialog says that the file holds what the code writes, unchecked by the app beyond the core's cap.
  - **`add-package` and `replace-package` keep what the file holds.** Both now take the package file whole, but conflicts: its crosswalks (checked as the schema checks them), solids (each as `define-solid` checks one, with the caps of a package's solids; one whose file the folder does not hold draws its placeholder and warns, as opening does), code, capabilities and what the code adds (as `set-package-code` checks them, capabilities and extensions going with the code). An update stores the new file's, removing what it leaves out, and refuses removing a solid something still shows. So "Update from another project" (ADR 0051) keeps a package's code, and since approval is by the hash of the code, its capabilities and its extensions, code that changed asks for approval again while code that did not keeps it. M14.2's flow from a file now sends `add-package` or `replace-package` alone, with the whole file, and a file with crosswalks is added or updated from a file too; files with solids or conflicts stay refused.
- 2026-11-02 (the main session, on M14.3's questions): `add-package` taking the whole file is kept, so crosswalks may come in from a file; `ChangesPreview.project` and the review store on `CodeStore.changes` are kept; exporters are saved by the browser, as every export is. **For M14.6:** "Update from another project" says when the code changed and will ask for approval again, as Packages… does; a solid kept from another project copies its `.glb` file into this project's `solids/` through the local program, rather than drawing its placeholder.
- 2026-11-02 (the user): **Claude's two tools, `list_package_actions` and `run_package_action` (M14.5), come after v0.1**, so that v0.1 is released sooner. Until then Claude reaches what packages add only through its existing tools; the decision on how it will run them, as Claude's proposals, stands.
- 2026-11-02 (M14.4, panels, by a builder):
  - **Which panels show.** For one selected element, the inspector shows, after the format panel, each panel of approved code that runs on this computer (as M14.3 offers actions: not waiting for approval, not turned off here, neither off after its calls stopped nor failed to load) whose file names no components, or names the element's component or one it derives from (`componentDerives`), in the order of the packages and of their files (`elementPanels` in `app/src/packages/offered.ts`). A package whose code does not run here shows no panel and no note: the inspector's Package code section already says where its code stands and reaches its review, and "Packages…" says why. None shows for a relation, a free shape or a selection of several.
  - **A section of its own, folded from its heading.** Each panel is an inspector section whose heading is a disclosure button, `aria-expanded`, holding its label in the package's words and "from the package “…”". Folding one is kept for the tab's session by package and panel, so the next element keeps it folded; a panel folded away is not called at all, so it costs the worker nothing, and unfolding it calls it.
  - **When it is called.** Its code is called with the panel's id and the element once the element and the project have stayed the same for 150 ms, and again as the project changes; one call at a time for each panel, a call asked for meanwhile starting once it ends, and only the answer of the call asked for last shown, every earlier one dropped (`LatestCall`). While the project changes, what the panel last showed stays until the new answer comes. New code, approved again, calls it afresh. A failure, a stop after 50 ms or an answer the core dropped (M14.1's problem, translated) shows inside the section with "Show again", and, as ADR 0089 has it, is not called again by itself: not as the project changes, nor as it is unfolded, only by Show again or another element.
  - **Drawn with the app's controls, every text as text.** A heading is an `h5`; a text a paragraph keeping its line breaks; value blocks next to each other one list of terms and values (true and false as Yes and No, numbers as the Simulation section writes them); a table a header row of column headers, cells, and a box of its own that scrolls and takes the focus, named by the heading before it, or the panel's; a chart plain SVG, as the Simulation section's: bars from a baseline at zero grouped by label, or lines over evenly spaced labels with a dot at each point up to 24, each mark with its series, label and number as a tooltip, the first and last labels and the range under it, a legend for more than one series, named for screen readers by its kind, series, count of labels and range, with its numbers in a table read by screen readers. Nothing a package answers is read as HTML.
  - **Series colors.** A chart's series take the overlay palette's colors (ADR 0080), each 3:1 against the canvas of both themes, in a fixed order, never cycled, reordered so that every two next to each other stay apart for the color-blind (blue, amber, violet, green, red, cyan; CVD ΔE at least 8.6 by the dataviz validator, in both themes). They are written as SVG fills and strokes, as an overlay's colors are, since no theme token holds six series; everything else is the theme's tokens. The legend and the table name each series, so color never carries it alone.
  - **Buttons run the package's actions on the element.** A button runs its action through M14.3's runner, with the element as the selection and the open view, whatever the action's `where` says, since a panel is a place of its own; its changes open in the review, and nothing changes until they are accepted. Buttons are disabled while the project cannot be changed or a comparison is shown, as the shape menu offers no action then.
