# Contents drawn as rows, the model's order, and what each view keeps collapsed

A component whose appearance draws its contents as rows shows each element its element holds in a view, through the view's nesting relation types, as one row: a band in the row's own fill, as wide as the shape, all of one height, stacked under a header in the model's order. The model's order is the order of `elements` in the model file; `create-element` can place a new element before another and `reorder-elements` moves elements, so row order is model data that git diffs and that Claude changes with the same commands. Changing the model's order never changes how a view draws its other shapes: the same action rewrites the stacking lists of every view and container whose drawing it would otherwise change, as ADR 0021's clarification asks, and a new element placed before others is still drawn in front of the shapes beside it. Rows have no positions of their own in any view: the core refuses one (`position-of-row`), dragging a row moves its container, and layout never writes one; the container's height always comes from its rows. A row does not draw what its own element holds; those elements' relations are drawn as aggregated relations on the row's sides, as a collapsed container's are, and the outline lists them. Only a rectangle or a rounded rectangle draws rows; a definition or element that sets rows on another shape is refused, and one that only inherits the combination is drawn as a rectangle and warned about on open. Relations that end on a row attach beside it, on the left or right side of its container at the row's middle, and relations that end on the container attach beside its header. Layout passes each copy of such a container to ELK as one block of the size its rows give, with a connection point on each side of every row that a drawn relation ends on, and places only the block. A collapsed one shows its header, with its rows' relations aggregated on it. A filter that hides a row leaves its line empty. An element added into a container goes through the nesting relation type whose limits name the two ends most closely (`nestingTypeFor`), so a column joins its table through "is column of" whatever else the view nests by, and the view starts nesting by that type in the same action when it did not. Deleting a container keeps ADR 0019: its rows stay unless the delete preview's choice to delete them is taken, which is offered checked only for rows that nothing else holds and that the open view draws as rows; the other elements it holds are listed unchecked, each with a container that keeps it when there is one. A view keeps the containers it shows collapsed in its own file, as a sorted list of element ids, so collapsing changes only that view (ADR 0007) and diffs as single lines; a deleted element leaves every such list. Visual Anything ships a built-in "Data modeling" package with Table, Column, "is column of" and "references", and reserves the ids of the packages planned for the domains it targets (`systems`, `data-modeling`, `data-science`, `neuroscience`, `physical-ai`), so that shipping one never stops a project from opening. We chose this because CONTEXT names a table as an element and a column's type as an attribute, so columns stay elements that relations, selection, filters and Claude can reach; because positions set by hand would drift from the rows' order and from layout; and because one trait any rectangular shape can use also serves enumerations, queues and classes.

## Considered options

- **Columns as a list attribute of the table**: rejected. A foreign key could not end on a column, and columns could not be selected, filtered or explained.
- **A `table` shape kind**: rejected. Rows are a way of laying out contents, which other components can use with their own shape.
- **Row order per view, or as an attribute of each nesting relation**: rejected. Order is part of what the model says, and numbering relations would rewrite many of them at each move.
- **Deleting columns with their table, always**: rejected, as ADR 0019 records; the preview offers it instead.
- **The view's first nesting relation type for new contents**: rejected. A type without limits, such as "is part of", would hold every column, and a view that nests only by "is column of" would show the tables empty.
- **Letting a reorder change how views draw**: rejected. Moving a row would reshuffle unrelated shapes in every view that leaves them to the model's order.
- **Collapsed state in the browser only**: rejected. Claude collapses through MCP, scenarios aggregate their steps through it, and a view read later should look as it was left.

## Consequences

A view that does not nest by the relation type holding a container's rows shows the container without rows and its contents as ordinary shapes; adding an element into such a container from the canvas adds that relation type to the view in the same action, and the inspector offers to show them as rows. An element held by two such containers has one order in both, and its relations attach to its first shape. ELK's connection points have one side each, so each related row gets two, and the side each relation uses is chosen before layout. The renderer keeps drawing order equal to hit-testing order among the shapes at one depth and splits a table's rows into bands, so tables stay within the frame budget. The built-in Data modeling package changes only by additions until built-in packages get versions (ADR 0018). Builds older than this refuse view files that hold `collapsed`. A change of container (ADR 0021) still keeps the type of the relations it leaves, or the view's first nesting relation type; dropping onto a table through the limits is for the drop design to settle.

- 2026-10-24: how the canvas draws rows and attaches relations to them.
  - **Where relations leave.** An end on a row leaves its table's left or right side at the row's middle, and an end on the table leaves beside its header: on the right when the other end's middle is at or beyond the table's middle, on the left otherwise, and on the right toward the middle of another relation; two ends beside tables that overlap horizontally both leave on the right. Each row with relations on a side, and the header, has a lane there, its place among them in the model's order, header first. A lane runs 12 + 4 × lane units out, and the seventh and later share the last, 36 units out, so that no stub reaches a shape the stand-in row placed 40 units away. Two ends on one side join in a C at the lane further out; facing stubs join in a Z through the middle of the gap; toward a shape above or below the table, the route turns vertical first, at its lane. Relations store nothing of this.
  - **Drawing.** A row is drawn one band above its table, in the tiles of its cell, so a tile of a tall table holds about 40 rows and an edit to one row redraws only its tile. A table draws its body (white until the look-and-feel track gives it a token per theme), its header band in its fill, a rule under the header and its border. A row draws its band in its fill inside that border, with a separator above it after the first, and no border of its own. Far out, a table is two blocks and its rows draw nothing. A row writes its name and detail only where details show, and from scale 0.7 on; the header writes its name, and its detail on the right, left of its toggle. A collapsed table keeps its header and foot on the sheet every collapsed container shows, 41 units tall so that its toggle fits, and writes "12 × Column".
  - **Gestures and keys.** A row moves its table; a box around a table selects the table, not its rows. Shift+Up and Shift+Down reorder a row, and Shift+Left and Shift+Right do nothing on one. Ctrl+Enter (⌘Enter) adds a row below the current row, or at the end of a table, and edits its name in place on that copy, where Ctrl+Enter adds the next row and Escape stops. Beside a row, a relation's line is pressed rather than the connect handle.
  - **Layout.** Layout never moves a row. Each table goes to ELK as one leaf of its size, with a port beside each row and header that a drawn relation ends on: east for a relation's source and west for its target, the other way round for a relation that closes a cycle.
  - **The inspector.** The Columns section (Rows, for any other component that draws rows) lists the rows in the model's order, moves them, adds one, and removes one only after the delete preview. It offers to show the rows a view leaves loose, and turns typed or pasted columns, `CREATE TABLE` included, into one action that relates each reference whose table and column it finds and lists the others.
