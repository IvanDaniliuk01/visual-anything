# Contents drawn as rows, the model's order, and what each view keeps collapsed

A component whose appearance draws its contents as rows shows each element its element holds in a view, through the view's nesting relation types, as one row: a band in the row's own fill, as wide as the shape, all of one height, stacked under a header in the model's order. The model's order is the order of `elements` in the model file; `create-element` can place a new element before another and `reorder-elements` moves elements, so row order is model data that git diffs and that Claude changes with the same commands. Changing the model's order never changes how a view draws its other shapes: the same action rewrites the stacking lists of every view and container whose drawing it would otherwise change, as ADR 0021's clarification asks, and a new element placed before others is still drawn in front of the shapes beside it. Rows have no positions of their own in any view: the core refuses one (`position-of-row`), dragging a row moves its container, and layout never writes one; the container's height always comes from its rows. A row does not draw what its own element holds; those elements' relations are drawn as aggregated relations on the row's sides, as a collapsed container's are, and the outline lists them. Only a rectangle or a rounded rectangle draws rows; a definition or element that sets rows on another shape is refused, and one that only inherits the combination is drawn as a rectangle and warned about on open. Relations that end on a row attach beside it, on the left or right side of its container at the row's middle, and relations that end on the container attach beside its header. Layout passes each copy of such a container to ELK as one block of the size its rows give, with a connection point on each side of every row that a drawn relation ends on, and places only the block. A collapsed one shows its header, with its rows' relations aggregated on it. A filter that hides a row leaves its line empty. An element added into a container goes through the nesting relation type whose limits name the two ends most closely (`nestingTypeFor`), so a column joins its table through "is column of" whatever else the view nests by, and the view starts nesting by that type in the same action when it did not. Deleting a container keeps ADR 0019: its rows stay unless the delete preview's choice to delete them is taken, which is offered checked only for rows that nothing else holds and that the open view draws as rows; the other elements it holds are listed unchecked, each with a container that keeps it when there is one. A view keeps the containers it shows collapsed in its own file, as a sorted list of element ids, so collapsing changes only that view (ADR 0007) and diffs as single lines; a deleted element leaves every such list. Visual Anything ships a built-in "Data modeling" package with Table, Column, "is column of" and "references", and reserves the ids of the packages planned for the domains it targets (`systems`, `data-modeling`, `data-science`, `neuroscience`, `physical-ai`), so that shipping one never stops a project from opening. We chose this because CONTEXT names a table as an element and a column's type as an attribute, so columns stay elements that relations, selection, filters and Claude can reach; because positions set by hand would drift from the rows' order and from layout; and because one trait any rectangular shape can use also serves enumerations, queues and classes.

## Considered options

- **Columns as a list attribute of the table**: rejected. A foreign key could not end on a column, and columns could not be selected, filtered or explained.
- **A `table` shape kind**: rejected. Rows are a way of laying out contents, which other components can use with their own shape.
- **Row order per view, or as an attribute of each nesting relation**: rejected. Order is part of what the model says, and numbering relations would rewrite many of them at each move.
- **Deleting columns with their table, always**: rejected, as ADR 0019 records; the preview offers it instead.
- **The view's first nesting relation type for new contents**: rejected. A type without limits, such as "is part of", would hold every column, and a view that nests only by "is column of" would show the tables empty.
- **Letting a reorder change how views draw**: rejected. Moving a row would reshuffle unrelated shapes in every view that leaves them to the model's order.
- **Collapsed state in the browser only**: rejected. Claude collapses through MCP, scenarios aggregate their steps through it, and a view read later should look as it was left.

## Consequences

A view that does not nest by the relation type holding a container's rows shows the container without rows and its contents as ordinary shapes; adding an element into such a container from the canvas adds that relation type to the view in the same action, and the inspector offers to show them as rows. An element held by two such containers has one order in both, and its relations attach to its first shape. ELK's connection points have one side each, so each related row gets two, and the side each relation uses is chosen before layout. The renderer keeps drawing order equal to hit-testing order among the shapes at one depth and splits a table's rows into bands, so tables stay within the frame budget. The built-in Data modeling package changes only by additions until built-in packages get versions (ADR 0018). Builds older than this refuse view files that hold `collapsed`. A change of container (ADR 0021) still keeps the type of the relations it leaves, or the view's first nesting relation type; dropping onto a table through the limits is for the drop design to settle.

- 2026-10-24: how the canvas draws rows and attaches relations to them.
  - **Where relations leave.** An end on a row leaves its table's left or right side at the row's middle, and an end on the table leaves beside its header: on the right when the other end's middle is at or beyond the table's middle, on the left otherwise, and on the right toward the middle of another relation; two ends beside tables that overlap horizontally both leave on the right. Each row with relations on a side, and the header, has a lane there, its place among them in the model's order, header first. A lane runs 12 + 4 × lane units out, and the seventh and later share the last, 36 units out, so that no stub reaches a shape the stand-in row placed 40 units away. Two ends on one side join in a C at the lane further out; facing stubs join in a Z through the middle of the gap; toward a shape above or below the table, the route turns vertical first, at its lane. Relations store nothing of this.
  - **Drawing.** A row is drawn one band above its table, in the tiles of its cell, so a tile of a tall table holds about 40 rows and an edit to one row redraws only its tile. A table draws its body in the theme's `rowsBody`, its header band in its fill, a rule under the header and its border. A row draws its band in its fill inside that border, with a separator in the theme's `rowSeparator` above it after the first, and no border of its own. Tables and rows therefore follow the theme even in stored colors, and a theme switch restyles their tiles in place (ADR 0033); a row writes its name, as its detail, in the color that reads on its fill. Far out, a table is two blocks and its rows draw nothing. A row writes its name and detail only where details show, and from scale 0.7 on; the header writes its name, and its detail on the right, left of its toggle. A collapsed table keeps its header and foot on the sheet every collapsed container shows, 41 units tall so that its toggle fits, and writes "12 × Column".
  - **Gestures and keys.** A row moves its table; a box around a table selects the table, not its rows. Shift+Up and Shift+Down reorder a row, and Shift+Left and Shift+Right do nothing on one. Ctrl+Enter (⌘Enter) adds a row below the current row, or at the end of a table, and edits its name in place on that copy, where Ctrl+Enter adds the next row and Escape stops. Beside a row, a relation's line is pressed rather than the connect handle.
  - **Layout.** Layout never moves a row. Each table goes to ELK as one leaf of its size, with a port beside each row and header that a drawn relation ends on: east for a relation's source and west for its target, the other way round for a relation that closes a cycle.
  - **The inspector.** The Columns section (Rows, for any other component that draws rows) lists the rows in the model's order, moves them, adds one, and removes one only after the delete preview. It offers to show the rows a view leaves loose, and turns typed or pasted columns, `CREATE TABLE` included, into one action that relates each reference whose table and column it finds and lists the others.

- 2026-10-25 (W24): a row in the inspector and the outline.
  - **Appearance.** While the open view draws every shape of an element as a row, its Appearance section says that a row is a band as wide as its container with no border of its own, and disables its Shape and Stroke, which describe that note; its size note stays, read in that light. The fill, the image and the ways back stay, and so does "Every Column", whose change also reaches the views that draw columns as shapes.
  - **In this view.** A membership that is a row says its place among the rows, "row 2 of 3, in the model's order", and that it moves with its container; it offers no stacking moves, no Take out and no Move to, since a row has no stacking order or position of its own. Other memberships of the same element keep them.
  - **The outline.** A row's own row lists last what its element holds, which the row does not draw, each as its name and "Not drawn: inside a row". Selecting one selects that element, and the canvas shows the row; an element that only rows hold is found in the first row that holds it, so the outline follows the selection there too.
- 2026-10-25 (W24): dropping shapes onto a shape that draws rows, which the Consequences left to the drop design.
  - **It takes a drop at once.** A shape that draws rows takes a drop anywhere on it, empty or collapsed too, without the rest a shape that holds nothing needs; a row under the pointer stands for its container, since it draws nothing of what it holds and never takes a drop of its own.
  - **What it takes.** Each moving element must be able to be one of its rows: a nesting relation type in use must accept the two ends by its limits. Where some nesting relation type names the container's component, or one it derives from, in its `to` limit, only those types count, so a table takes columns through "is column of" and refuses a Service although "is part of" sets no limits; a component of one's own that draws rows and that no limit names takes whatever a nesting relation type accepts. Of the types that count, the one `nestingTypeFor` chooses for the two ends is used, else the first the view nests by, else the first. Anything else is refused before release, outlined as refused, with the caption "Cannot put inside "users"" and why, such as `Only a Column can be a row of "users", through "is column of"`; let go there, the shapes only move. A container inside what moves is refused as before.
  - **Where it lands.** At the place under the pointer: before the row whose upper half it is over, after one whose lower half it is over, first over the header, last under the rows or on a collapsed one. A bar across the container shows the place, and the caption says it: `Make it a row of "users"`, then `Before "email"`, `After its last row` or `As its first row`, the relation type when the view nests by several or starts nesting by it, and `Alt: move only`. Snapping keeps the frame the shapes sit in, since a row has no position.
  - **One action, named as a change of container** (`Put "phone" inside "users"`): the view starts nesting by the relation type when it does not yet; the nesting relations that placed the elements where they were are deleted, with what cascades, after the same question a change of container asks; one relation of the chosen type puts each inside, unless one already does; and a `reorder-elements` puts them at their place in the model's order, just before the row after it or just after the last row, and only when they are not there already. It does not use `change-container`, whose bringing to the front would write a stacking list for a container whose rows have none, as `reorder-elements` already leaves such containers out; whatever else is selected moves along in the same action.
- 2026-10-25: `change-container` into a shape that draws its contents as rows makes what enters a row in the model's order. It writes no stacking list for that container, as `reorder-elements` already does not, since rows have no stacking order.

- 2026-10-29: **ADR 0080 supersedes part of this ADR**, stage by stage as milestone M3c builds it:

- 2026-10-29 (M3d): **Data modeling holds a whole database.** The first real model (one PostgreSQL database with 9 schemas, 73 tables and 19 views) had to make these in a package of its own. The package gains them by additions only: no id it had changes, and "is column of" only widens its limits.
  - **Components:**
    - Schema, a namespace of a database that holds tables, views, enums, functions, triggers and sequences;
    - View, a named query read as a table, which draws its columns as rows as a table does;
    - Materialized view, a view whose rows the database stores;
    - Enum, with `values`;
    - Function, a function or a procedure, with `language`, `arguments` and `returns`;
    - Trigger, with `timing` (`before`, `after` or `instead of`), `events` and `level` (`row` or `statement`);
    - Sequence, with `type`, `start` and `increment`.

    The column gains `default` and `check`.
  - **Relation types**, all directed and derived from "relates to":
    - "reads from", from a view or a function to a table or a view;
    - "writes to", from a function to a table, a view or a sequence, since taking a sequence's next number changes it;
    - "fires on", from a trigger to a table or a view, since PostgreSQL's `INSTEAD OF` triggers fire on views;
    - "runs", from a trigger to a function.

    "Is column of" now also places a column in a view.
  - **Everything derives from Essence, Schema included.** Table does, so the package needs no other and keeps opening alone. Deriving Schema from Systems' System would make Data modeling need Systems and hand schemas a team `owner` and a system's look. A project's own schema component derived from System, as the first real model made, stays valid.
  - **A schema sits in its database, and what it holds in it, through Systems' "is part of".** The package defines no "is part of" of its own. The database is Systems' Database, so a project with schemas uses Systems already. The SQL recipe and the first real model already nest that way, so one view nests by `systems.is-part-of` and `data-modeling.is-column-of` from database to column. A second "is part of" would split nesting between views, and `nestingTypeFor` would choose it over Systems' for every table dropped into a schema.
  - **View and Materialized view are two components, not one with a `materialized` attribute.** Materialized view derives from View, so a limit or a filter that names View takes both, while the palette, filters and appearances still tell them apart. That is also how the first real model's own package drew them.
  - **View derives from Essence, not from Table.** A view is not a table: a filter, a limit or "references" that names Table would take views too. It draws its columns as rows, so "is column of" names both in its `to` limit.
  - **No code is held.** No attribute holds a view's query, a function's body or a trigger's condition. Every attribute that comes from the material is text as written (`arguments`, `returns`, `events`, a column's `default` and `check`), and nothing reads it as code. No attribute has a default, so every value is data. `timing` and `level` take lower case, as `onDelete` does; values outside their choices only warn.
  - **An enum's `values` is one text, separated by commas,** not JSON, so that a shape writes it in its detail and filters compare it as text. A column of an enum's type names the enum in its `type`; no relation type joins them yet.
  - **The names.** "reads from" and "writes to" share their English names with Systems' relation types, whose limits are a service and a data store; the ids and limits tell them apart. The component View keeps the SQL word: its description says it is a view of a database, never a view of the model. In Spanish: Esquema, Vista, Vista materializada, Enum, Función, Trigger and Secuencia; "lee de", "escribe en", "se dispara en" and "ejecuta".
  - **Appearances.** Each new component has its own colours, with a dark shade for each color it sets that meets ADR 0033's thresholds, and its own icon. The icons are plain SVG drawn for Visual Anything, CC0-1.0 (ADR 0047, ADR 0051), each in one colour that reads at 3:1 on its component's fill in both themes. Table and Column keep no icon, so tables already drawn look the same.
  - **The SQL recipe** makes one `systems.database` for the database. Each `CREATE SCHEMA` becomes a Schema inside it, never a database per schema. Views, functions, triggers, enums and sequences become their components, with what each reads from, writes to, fires on and runs, never their code. The material's text is written as text, as the material writes it.
  - **Built-in packages stay closed.** `define_component` and `define_relation_type` refuse a built-in package before the core does. The refusal says that built-in packages are closed and names a definition the package already has under that name. It gives the call that derives the definition in the project's first package of its own, or in one `create_package` makes first.
  - **A project's own database package keeps working.** It opens with the same warnings as before, and the README says how to move such a model onto these components with `update_element` and `update_relation`.

- 2026-10-30 (M3d, "Fixes from use"): **a column names its enum through "has type".** This refines the 2026-10-29 clarification, where a column of an enum's type named the enum only in its `type`. Data modeling gains the relation type "has type" (`data-modeling.has-type`), added after the others, since built-in ids only grow.
  - It is directed, derived from "relates to", from a Column to an Enum, and does not nest.
  - It is drawn dotted in the enum's brown (`#8A4B0F`, `#EBA65E` in the dark theme), as the enum is.
  - Its Spanish name is "tiene tipo".
  - The column keeps its `type` as written, `shop.order_status` included: the relation says which enum that is, so that a filter, focus and the canvas follow it.
  - The SQL recipe draws it for each column whose type names an enum the material creates, by its schema-qualified name or by its name within its schema, and for no other type, such as a domain or a type of an extension.
