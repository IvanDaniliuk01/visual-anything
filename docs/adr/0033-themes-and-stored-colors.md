# Themes come from one source; stored colors are drawn as stored, built-in colors have a shade for each theme

The app and the canvas are drawn in a theme, light or dark, which follows the system unless the person chooses one (ADR-0032). These choices fix what a theme colors and where its colors come from:

- **One source.** The colors of both themes live in one TypeScript module, `packages/app/src/theme/themes.ts`: the panels' colors and the canvas's own, the canvas taking the panels' value wherever the color is the same. A generator writes the panels' colors and the scales of `theme/scale.ts` as a static stylesheet, `theme/tokens.css`, which the app's stylesheet imports first; a test fails while the committed file differs from what the module generates. The renderer takes the canvas's colors from the same module, since PixiJS cannot read CSS variables. The page says which theme it shows with `data-theme="light"` or `"dark"` on its root element; without one, the stylesheet follows the system. No stylesheet writes a color out: each uses the tokens.
- **Contrast.** In both themes every text pair the app uses meets 4.5:1, and every control boundary, focus ring, selection and other mark 3:1. Tests check each pair, including those of the canvas's own colors.
- **Stored colors.** Every color stored in a project is `#RRGGBB` and is drawn exactly as stored in the light theme and the dark theme alike: the colors of the project's own components and relation types, of project appearances, of an element's or a relation's own appearance, and of notes and free arrows. Commands write new colors in capitals and keep the stored spelling of a color equal to it ignoring case; nothing rewrites a color read from a file. Colors stay `#RRGGBB`: no transparency, names or CSS values.
- **Built-in colors.** The colors built into Visual Anything, those of built-in packages, Essence and "relates to", have a shade for each theme, kept in `core` beside the definitions: the light theme draws the colors the definitions give, and the dark theme a shade of each made for the dark canvas. A color trait takes its built-in dark shade only while nothing in the project sets it, except that a built-in fill keeps its light value beside a stored stroke that is under 3:1 against the dark canvas, so that the shape keeps the pair the light theme shows instead of vanishing. Setting a color anywhere draws that exact color in both themes, and removing it brings back the built-in shades.
- **What the theme colors.** The theme also gives the colors the project does not define: the canvas, the grid and the rulers, selection and highlight marks, label backs, the casing under every line, and notes and free arrows without colors of their own. Text on a shape or a note takes the color that reads on the fill it is drawn on. A stored color that is hard to see in one of the themes is pointed out where it is picked and in Claude's tool results, and is never refused.

We chose this because the person asked to pick any color and see that color; because the built-in look, which most shapes use, then looks made for the dark canvas instead of light shapes on a dark ground; because files, git diffs and what Claude reads stay the same in both themes; and because one source of theme colors keeps the panels and the canvas from drifting apart.

## Considered options

- **Colors written in each stylesheet, or CSS variables the canvas reads at run time**: rejected. PixiJS cannot read CSS variables, jsdom loads no CSS for tests, and two copies of each color drift.
- **Tokens injected by script at run time**: rejected. The first frame would wait for the script, and a page policy without `'unsafe-inline'` styles would need more exceptions.
- **Built-in colors moved once to mid-tones that read on both canvases, everything drawn as stored**: rejected. The light theme loses contrast it has today, and the dark theme shows white and pastel blocks.
- **Every color adapted to the theme when drawn**: rejected. The dark theme would not show the colors people pick, and Claude would read other colors than the person sees.
- **Each built-in trait taking its dark shade on its own, whatever is stored beside it**: rejected. A stored stroke beside a built-in fill's dark shade can leave a shape at 1.2:1 against the dark canvas.
- **Named colors that follow the theme, stored in files beside #RRGGBB**: rejected for v0.1. Older programs would refuse files that use one, and everything that draws or compares a color would have to resolve names first. It can come later as its own additive change.
- **A dark variant beside each stored color**: rejected. It doubles every appearance, command and tool.
- **Inverting the canvas with a filter**: rejected. It changes the colors people pick.

## Consequences

After changing `themes.ts` or `scale.ts`, `tokens.css` is generated again and committed with them. A theme switch builds new drawings for the tiles drawn in built-in colors, within the renderer's frame budget and behind the old drawings, and then shows the canvas and the panels in the new theme in one frame; tiles drawn only in stored colors keep their drawings. A color picked against the light canvas can be bright on the dark one, and the picker shows how it reads in both. Changing a built-in color or its dark shade changes every project's look, as ADR-0018 intends for improvements of built-in packages. Export, after v0.1, chooses a theme.

## How the canvas follows the theme

<!-- Decided by Claude on 2026-10-25 under the user's standing delegation of design decisions, building W17. -->

- **The way in.** `renderer.setTheme(THEMES[name].canvas)` draws the canvas in a theme; before the canvas has started it only keeps the theme, and the canvas starts in it, its background included. `CanvasArea` takes `theme` and `onThemeShown`, and `Shell` passes the theme of `usePreferences()` and the function of `useThemeHold(view !== undefined)`, so that `data-theme` changes in the frame the canvas first shows the theme. `canvas/palette.ts` became `canvas/colors.ts`, whose values are the light theme's from `THEMES`.
- **What the scene carries.** `ElementShape.dark` and `RelationLine.darkStroke` hold the dark theme's colors from the core's `darkColorsOf` and `relationDarkStrokeOf`, only where they differ from the light ones; an aggregated relation takes its relation type's. Drawing takes painted copies of shapes, lines, notes and arrows (`canvas/theme/paint.ts`), so `draw.ts` draws any theme as it draws the light one. Notes and free arrows without colors of their own take the theme's through the core's `noteColorsOf` and `arrowColorOf`, with no dark rule of their own, so that the canvas draws what the inspector says.
- **Theme-independent drawing.** A plain block is outlined when its fill is under 3:1 against either theme's canvas, so that a block in stored colors is drawn alike in both themes. A container's toggle is drawn in the container's colors with its sign in the text that reads on them. Relation casings, the same route stroked 2 units wider and solid, are drawn in white in a drawing of their own and tinted to the canvas; a free arrow's casing is drawn in the canvas color with it. The selection's boxes and glows are drawn in white and tinted to the theme's selection color; hover is the selection color, thinner.
- **Labels are tinted, never written again.** Every label font is white. A shape's name and detail are tinted to the text that reads on the fill drawn; a relation's name to the theme's text, over a back tinted to the canvas; a note's text, drawn white, to the note's text color. Each label is recorded with what its tint follows, and tinted again when its tile's stamp changes. Backs tinted to the shape under the label come later.
- **Restyles.** Each tile's plain and full drawings and its labels carry a stamp: the theme they were drawn in when they follow the theme, and how many times the colors of what the tile draws changed. While a switch or a recolor is pending, the stale drawings that show are drawn again for the new stamp behind the old ones, nearest the middle of the screen first, within 6 ms a frame and at least one tile a frame, their geometry built inside that clock through the renderer's graphics context system. In the first frame where none is left on screen, or 30 frames after it began, all are shown at once by giving their drawings the new contexts, with the background, the casings' tint, the marks, a drag's drawing and the labels on and near the screen; the contexts replaced are destroyed once that frame is rendered. Stale drawings off screen keep showing nothing until they come near, and are drawn again then, or while the camera rests; a full drawing is never dropped for being stale. The plain drawing of relations whose lines are all thinner than half a device pixel on screen shows next to nothing and is not waited for. `renderer.stats` counts the frames each switch took, the tiles shown stale after one, and fallbacks.
- **Recolors in place.** When a scene keeps a tile's key and its shapes, lines or free shapes differ only in their colors (`fill`, `stroke` and `dark` of a shape, `stroke` and `darkStroke` of a line, the colors of notes and arrows; every other field, including one added later, counts as a change of the drawing), the tile is kept and restyled as a switch restyles it, so a recolor shows in one frame with no tile falling back to its plain drawing.
- **The benchmark** judges theme switches and the recolor by A1's and A2's rule, 95% of frames within 16.7 ms and every frame within 33 ms, and reports after how many frames each showed, the fallbacks and the stale tiles shown. `?theme=dark` runs it in the dark theme.

## Clarifications

<!-- Decided by Claude on 2026-10-25 under the user's standing delegation of design decisions. -->

- 2026-10-25 (A3): the grid, the rulers and the readout beside a drag take their colors from the canvas's theme. The grid draws `gridLine` at `gridStrength` times each family's strength, and `gridSnapAlpha` is the alpha the lines 8 canvas units apart keep while snapping, once they are 8 px apart on screen (0.05 light, 0.04 dark: decorative, about 1.10:1). The rulers draw `rulerBand`, `rulerBorder` and `rulerText`, and the selection's extent on them `selected`. The readout takes the shell's `surfaceRaised` and `text` of the same theme, with a `rulerBorder` edge. Grid lines and ticks are drawn white or in the theme's colors once, and `renderer.setTheme` gives the grid and the rulers the new theme in the frame that shows the rest of the canvas in it: the grid is retinted, and drawn again only where the two themes' strengths differ.
- 2026-10-25 (A2): the inspector shows colors in the theme the person's preferences draw the canvas in (`usePreferences().theme`, through `useShownTheme`), as the canvas draws them there: an element's through the core's `drawnColorsOf`, a relation's through `drawnRelationAppearanceOf`, notes and free arrows through `noteColorsOf` and `arrowColorOf` with that theme's canvas colors, and a component or a relation type at its level through its dark colors or dark stroke. A pick is compared with what the shape would show in that theme without a color of its own (`PickOptions.theme`), so picking the color shown records nothing in either theme, picking what it would show without its own takes its own back, and picking a built-in color's light value on the dark canvas stores it as a color of its own, drawn as stored in both themes. The hints under a color still look at both canvases.

- 2026-10-25 (W42): **what Claude's tool results point out.** A tool that stores a color for Claude (`set_appearance`, `update_element`, `update_relation`, `add_to_model`, `add_free_shape` and `update_free_shape`) adds a warning to its answer, after the core's, for each canvas where what it set is hard to see, by the core's `contrastRatio`, `CANVAS_BACKGROUNDS` and `MINIMUM_MARK_CONTRAST`, with the ratio cut to one decimal as the legend writes it: a stroke it set under 3:1 against the light or the dark canvas (`The stroke #FFFFFF of "API" is 1.0:1 against the light canvas, under 3:1.`); and an element, a component or a note whose fill and stroke, as the project now draws them in that theme, are both under 3:1 against its canvas (`"API" blends into the light canvas: …`), the inspector's rule. A note without a stroke of its own takes the theme's, which reads. Text needs no warning: the canvas writes a shape's or a note's text in black or white, whichever reads on its fill, and the better of the two is at least 4.58:1 on any #RRGGBB. The color is stored all the same; only a color not written as #RRGGBB is refused, by the core, with `invalid-appearance`.
- 2026-10-25 (L1 review): an image's tint is a stored color like the others: picked again in another case, it keeps the spelling stored in that place, so the project does not change and no action is recorded. The core's `CANVAS_BACKGROUNDS`, against which it measures the contrast of stored colors for the hints and Claude's tool results, copies the two canvas colors of `themes.ts`; a test in the app asserts that each equals `THEMES[name].canvas.background`, so the two never part.

- 2026-10-26 (W49): **a shape is always told apart from the container it sits in.** Dogfooding found modules inside a module of the same fill disappear far out. Its outline now shows at any zoom, a device pixel wide at least (ADR 0014's clarification of this date), and a shape inside a container whose stroke is under 3:1 against its own fill is outlined in the color that reads on its fill (`outlineColorOf` in `canvas/colors.ts`: `readableTextColors(fill).detail`), on the canvas, far out and in the SVG. In a container of nearly its own fill, its boundary then meets the 3:1 this ADR asks of every mark; a shape directly on the canvas keeps its stroke as stored, since blocks that would not stand out from the canvas are outlined already. Considered: tinting a container's fill away from its contents' fills, rejected, since stored colors are drawn as stored and the canvas would then show colors nobody chose; comparing each shape with its container's fill, rejected, since a tile's shapes would then depend on another tile's, and a recolor of a container would have to draw its contents again.

- 2026-10-31 (A4): **no stylesheet writes a design value out.** `theme/stylesheets.test.ts`, which takes in the color test of A1, reads every declaration of every stylesheet but `tokens.css` and fails on a length in `px`, `rem`, `em` or another absolute or font unit, a color by its code, its function or its CSS name, a bare number for `z-index`, `font-weight`, `line-height`, `font-size`, `stroke-width` or `stroke-dasharray`, an outer shadow that is not one of the elevation tokens, and a variable nothing defines without a fallback. It allows only what is no design value: zero in any unit, percentages, `fr` and the viewport's units, which share out the room there is; `ch` and `lh`, which count the characters and lines a box holds; angles and times; and media conditions, which cannot read a variable. The scales of `theme/scale.ts` gain what the stylesheets lacked:
  - **spaces and sizes named by their length in hundredths of a rem** (`--space-35` is 0.35rem, `--size-2200` 22rem): the steps the panels were built with, kept so that no layout moved, and the old `--space-1` to `--space-6` became `--space-25`, `-50`, `-75`, `-100`, `-150` and `-200`; a later pass may fold neighbors together, one step at a time; `--size-hidden` is the one-pixel box of what only screen readers read;
  - **lines**: `--stroke-thin` 1px, `-medium` 1.5px (the tour's leader line), `-thick` 2px (the focus ring, a chart's line), `-mark` 3px (the bar of the current row), `-bar` 4px, and `--stroke-dash` 4 3; an offset inward is `calc(-1 * var(--stroke-…))`, and a chart's SVG strokes take them as user units, a pixel each;
  - `--em-*` for lengths relative to the text they sit in (emphasis headings, code, a link's underline, the gutter of line numbers), `--tracking-title` and `--tracking-caps`, `--icon-sm` 16px and `--icon-md` 24px, `--radius-xs`, `--line-none` and `--line-relaxed`, `--weight-normal`, and `--z-marks` under the toolbar for comment pins.

  What could not stay to the pixel was folded onto the scales it belongs to: text sizes onto the type scale's nearest step, and those under its 12 px floor (0.65rem to 0.8rem) onto `--text-xs`; radii onto the nearest step, a tie going up (0.3rem and 4px to `sm`, 0.35rem to `md`, 0.5rem to `lg`, 2px to `xs`); line heights of 1.35 and 1.4 to `normal`; letter spacing of 0.04em to `caps`; spaces of 2px and 4px to `--space-15` and `--space-30`; and the guidance card's 0.25rem bar to `--stroke-bar`. The Explore panel stacks as a menu (`--z-menu`), as the find bar's list does, rather than at the editor's level.
- 2026-10-31 (A4): **every control shows its four states.** `styles.css` gives every control the focus ring and the muted look of what cannot be used, at no specificity; a control whose stylesheet gives it a look of its own (a background, a color, a border, a shadow or an outline) takes over what the browser and those shared rules would show, so its rules give it hover and pressed, disabled when it sets a color, and focus-visible when it sets an outline. `theme/controls.test.ts` finds the controls in the components' source (buttons, fields, lists of choices, disclosures and menu items, with their classes) and checks their rules, counting a rule for the same control in a wider place (`.inspector input:disabled` for `.inspector input[type='text']`), for the base class written beside a modifier on the same element (`.scenario-button` for `.scenario-record`), and for the element it is written on (`.canvas-menu button` for `.canvas-menu .canvas-menu-cancel`); a disclosure's summary has no disabled state in HTML. A field under the pointer or pressed takes `--text-muted` as its boundary, a neutral button `--surface-hover` and `--surface-pressed`, a link-like one its underline or text color. A primary action under the pointer or pressed takes the new `accentFillHover` (#163D70 light, #A8C7FA dark, its text at 4.5:1 in both, as `contrast.test.ts` checks); before, the dialogs' and the proposal's own hover outranked the primary fill and left its white text on a light ground.
- 2026-10-31 (A4): **one icon set.** Every icon a panel, menu or toolbar shows comes from `shell/icons.tsx`: the import's icon and the product's mark moved there, the stacking moves joined it, and close buttons, the tree's branches, a sorted column and the comments' way back draw its icons instead of the characters ×, ▸, ▾, ↑, ↓ and ←. `shell/icons.test.ts` fails on an `<svg>` written in another component, on a character standing alone for an icon or opening a translated text, and on one in a stylesheet's `content`; an arrow inside text, as in "A → B" or before an end's name, is text. Its lists allow the drawings that are no icons (the Simulation section's chart, the tour's leader line) and the canvas's toolbar, whose own stacking icons and "−" for Zoom out wait for the canvas task to leave `canvas/`.
- 2026-10-31 (A4): **every empty state says what to do next**, naming the control that does it as the app labels it, in English and in Spanish; where nothing can be done, as in the read-only page, it points at another view or at whoever shared it. The canvas's own, "This view has no shapes yet." in `canvas/CanvasArea.tsx`, says it too since the toolbar took the set's icons, the same day.
